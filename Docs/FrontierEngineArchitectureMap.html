    03 How It Actually Runs on Your GTX 1650 SUPER (Hardware X-Ray)

    Why a 1,280-core Turing GPU takes 12.38 ms on a 960×650 viewport — and how Phase 1 & Phase 2 change hardware utilization

    1. The Single-Queue FIFO Domino Effect Root Cause of UI/Insp Spikes

    VulkanInterchange creates 1 queue (PrimaryQueue) shared by World Compute, Precompute, Gizmo, VectorCanvas, and ImGui. In Vulkan, all submissions to one queue execute in strict FIFO order. If ANY tiny UI texture upload calls AwaitTimelineTick, the CPU freezes until the entire 12 ms World Compute pass ahead of it finishes!

    *Remaining sync point: when an Inspector card redraws via VectorCanvasRasterizer or uploads a new texture in ImGuiOverlayRasterization:991, it still calls AwaitTimelineTick — queued for Phase 2 cleanup.

    2. Why ComputeEntry Takes 12.38 ms on GTX 1650 SUPER SM Occupancy

    Right now, one single compute shader (WorldViewportRadiometricCompute.slang, 4,647 lines, 197 KB SPIR-V, compiled -O0) does EVERY job per pixel in one giant 8×8 dispatch: primary BVH4 ray trace + triangle shading + OpenPBR + shadow PCSS + 3D GDF AO + 3D Radiosity GI + specular reflections + sky LUT + clouds + local fog.

    3. GPU VRAM Layout & Descriptor Architecture (38 Bindings per Compute Dispatch) DEVICE_LOCAL VRAM

    Scene Geometry & Acceleration (Slots 1–3, 31)
    • BvhEntryBuffer (Slot 1): Wide 4-lane BVH nodes (128 B/node). Top-level reserved headroom + per-instance subtrees.
    • ShadedTriangleBuffer (Slot 2): World-space triangles (96 B/tri) updated in VRAM by WorldInstanceTransformCompute (P1).
    • ResidentLocalBvh/TriBuffer (P1): Immutable local-space templates in VRAM so drags never touch PCIe or CPU.
    • ActiveClusterMaskBuffer (Slot 31): Dual-slice Nanite LOD bitmask (Slice 0 = finest for shadows/GDF, Slice 1 = camera LOD).
    Hardware 3D Volumes & Shadow/Sky (Slots 5, 7, 32–37)
    • GdfFineImage3D / GdfCoarseImage3D (Slots 32–33, P1): 64³ R16_SFLOAT hardware 3D textures + VK_FILTER_LINEAR + REPEAT (1 TMU fetch vs 8 SSBO fetches).
    • RadiosityMip0/CoarseImage3D (Slots 34–35, P1): 64³ + 32³/16³/8³ RGBA16F hardware 3D mip pyramid.
    • SolarShadowDepthBuffer (Slot 5): 2-cascade orthographic shadow depth SSBO.
    • AtmosphericSkyViewLutBuffer (Slot 7): Packed SSBO (SkyView 192×108 + Transmittance 256×64 + MultiScatter 32×32) — Phase 2: convert to 2D texture!
    Per-Pixel G-Buffer, Ping-Pong & Display (Slots 4, 6, 10–17, 26–27)
    • 9 full-res RGBA32F (16 B/px) SSBOs: AccumulationHdr, GBufPosMask, GBufNormAo, GBufDirectBase, GBufSunContrib, GBufAlbedo, Ping/PongShadowAo, Ping/PongIndirect.
    • At 1920×1080 that's ~33 MB/frame written + read in raw float4 SSBOs (Phase 2: pack to RGBA16F/R11G11B10F = 2×–4× less VRAM bandwidth!).
    • OutputPixelBuffer (Slot 4) → vkCmdCopyBufferToImage → DisplayOutputImage2D (sampled by Gizmo & ImGui).

    05 Forensic Diagnosis: The GTX-Only Vertical Sky & Ground Line Bug

    Exact root cause of the ~14 px razor-sharp pale stripe visible in your screenshots on GTX (not RTX)

    Why It Appears on BOTH Sky & Ground at the Exact Same X 100% Diagnosed

    • Compass proof from your 2 screenshots: In both images, the bottom-right XYZ compass shows +X pointing back-right and +Y pointing left — meaning the vertical stripe sits strictly on the -X world axis (Dir.x < 0, Dir.y ≈ 0 ⇒ Azimuth = ±π) and orbits with the world!
    • Width proof: SkyViewLUT is 192 texels wide (360° / 192 = 1.875°). The half-texel where FX < 0 is 0.9375°. On your viewport (~65° HFOV, ~840 px wide), 0.9375° / 65° × 840 px = 12–14 px — an exact pixel match with razor-sharp edges at U = 0 and U = 0.5/192!

    Why It Only Happens on GTX (Turing) and NOT RTX SPIR-V -O0 OpSRem

    In Engine/Shaders/Atmosphere/SkyViewTransmittanceCompute.slang lines 177–200:

    // SkyViewTransmittanceCompute.slang:177-200 float Azimuth = atan2(Dir.y, Dir.x); float U = frac(Azimuth / AtmoTauConst + 0.5); float FX = U * float(W) - 0.5; // ∈ [-0.5, 0.0) ONLY when U ∈ [0, 0.5/192) int IX0 = ((int(floor(FX)) % W) + W) % W; // floor(FX) = -1 → signed OpSRem(-1, W)! int IX1 = (IX0 + 1) % W;

    We inspected the actual compiled SPIR-V binary (WorldViewportRadiometricCompute.comp.spv) and confirmed slangc -O0 emits three signed OpSRem instructions with a runtime UBO divisor W:

    OpConvertFToS %3541 = int(floor(FX)) // = -1 inside the 14px -X stripe OpSRem %3542 = %3541 % W // negative signed remainder on Turing -O0 OpSRem %3544 = (%3542 + W) % W OpSRem %3546 = (%3544 + 1) % W
    Fixed in Phase 2 (Commit 306820fe — 100% immune on all GPUs):
    1. Strictly unsigned azimuth wrap: Eliminated negative FX and all 3 signed OpSRem instructions in SkyViewTransmittanceCompute.slang via float FXPos = U * float(WidthPx) + float(WidthPx) - 0.5; uint UX0 = uint(FXPos) % WidthPx; (100% OpConvertFToU + OpUMod, never negative).
    2. 2× fewer SkyView memory fetches: Replaced 4-row Catmull-Rom (8 SSBO reads) with horizon-clamped smoothstep bilinear (4 reads), preserving bank boundaries while cutting SkyView bandwidth in half.
